# 个人空间、挂载与团队空间

## 账号、空间与文件内容

Omnora 的功能归属于账号：**文件、回收站、分享、AI Token、文档和账户设置**均以当前登录账号为主体。空间不是第二套功能入口，而是文件内容、挂载和权限的范围。

- **个人空间**：每位账号的系统托管文件空间，物理目录固定在 `OMNORA_PERSONAL_STORAGE_DIR/<account-id>`；默认根为 `/var/lib/omnora/personal`。它不在 NAS 插槽下创建文件夹。
- **团队空间**：账号可创建、可加入的共享空间。具体团队空间在文件内容区作为第一层文件夹展示；进入后才查看该空间的挂载和目录。左侧只用“个人空间 / 团队空间”选择文件范围，不能把具体空间或账号功能拆成两套 Tab。
- **外部挂载**：管理员把已经存在的 NAS 目录 bind mount 到容器，例如 `/volume1/photo:/mnt/omnora/slot2:rw`。注册 `/mnt/omnora/slot2` 后，该目录就是挂载根，根目录原有内容可直接浏览。

切换空间只改变文件、搜索、挂载和回收站的内容上下文；不会改变分享、Token、文档或账户设置的数据归属。

## 团队空间存储与成员

任意状态为 `active` 的账号都可创建团队空间。创建者自动成为 `manager`，服务器创建默认的托管读写挂载：

```text
<ManagedDir>/team-spaces/<space-id>
```

该路径只由服务端生成，客户端和普通成员不能提交、配置或看到宿主机绝对路径。团队空间成员由该空间的当前 `manager` 管理：

- 成员权限为 `viewer`、`editor` 或 `manager`；新增成员默认 `viewer`。
- 成员引用可使用账号 ID 或大小写不敏感的邮箱，但只能解析到 `active` 账号。
- 最后一个 `manager` 不能被删除或降级，操作返回 `last_manager_required`。
- 个人空间不能通过团队成员接口修改，操作返回 `personal_space_protected`。

外部 NAS 插槽不会自动创建 `<slot>/<space-id>` 子目录，也不会因为团队空间而改变已有根目录内容。团队空间的专用目录仅位于受控的 `ManagedDir/team-spaces` 下。

## 公开分享与 MCP

浏览器会话创建公开分享仍要求调用账号在目标空间是 `manager`。MCP 的授权独立于浏览器规则：使用 `space_grant` 的 AI Token，在满足以下所有条件时，空间 `editor` 可以创建公开分享：

1. Token 包含 `shares:create` scope；
2. Token 对目标空间的 grant 至少为 `editor`；
3. Token 所属账号的实时空间 ACL 至少为 `editor`；
4. 目标挂载可写，目标文件夹不在该 Token 的黑名单中；
5. 通过既有 MRTR、确认、挂载身份和路径安全检查。

`viewer`、只读挂载、黑名单目录及其子目录、失效账号或已撤销 ACL 必须拒绝创建分享。AI Token 的空间 grant 和文件夹黑名单都属于账号级配置，可在后续编辑；黑名单目录及其子目录禁止该 Token 经 MCP 访问。

## 已知延期问题（P2）

以下两项只记录，不在本次团队空间实现中修改：

1. **回收站导航状态不一致**：切换到不支持回收站的挂载时，入口隐藏但 `activeTab` 仍可能是 `trash`，内容显示空态。
2. **黑名单指纹采集早于 ACL**：创建或编辑 AI Token 时，服务端可能在确认账号空间 ACL 前解析挂载并采集 denylist 目录指纹。

后续修复应分别保证导航状态与内容一致，以及先验证账号 ACL/grant 再访问挂载或目录身份。
