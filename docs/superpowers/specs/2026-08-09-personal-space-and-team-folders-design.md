# 个人空间与团队文件夹设计

## 1. 目标

将成员端当前“我的文件”替换为可直接管理的“个人空间”，并增加独立的“团队文件夹”一级入口，以展示当前账号获权的共用存储。移除个人空间的“可读写”状态文案，改为通过可执行工具栏和文件行操作表达能力。

## 2. 信息架构

成员端侧栏文件区域固定为三个一级入口：

1. `个人空间` / `Personal space`
2. `团队文件夹` / `Team folders`
3. `协作` / `Collaboration`

登录后默认打开个人空间根目录，不再先显示“个人空间”卡片或内容源目录。团队文件夹进入后显示当前账号具备有效授权的共用存储卡片；点击卡片后打开对应根目录。

个人空间、团队文件夹和协作都继续使用账户内容源模型，禁止恢复 Space REST 路由或向成员端暴露默认挂载 ID、服务器路径和旧 Space 坐标。

## 3. 个人空间直接管理

个人空间根目录加载成功后，显示：

- 上传；
- 新建文件夹；
- 刷新；
- 在目录内返回上一级；
- 文件或文件夹行的打开、下载、重命名、移动、复制、删除和分享操作。

个人空间是当前账号的受保护个人目录，前端将其视为可写来源。个人空间页不显示“可读写”文字。若服务端仍返回写入失败、身份异常或目录不可用，保留现有错误和 fail-closed 行为；前端不能通过隐藏状态文案绕过服务端授权。

空目录文案改为引导式提示：上传文件或新建文件夹即可开始。

## 4. 团队文件夹

团队文件夹页面从 `GET /api/v1/member/content-sources` 的 `commonMounts` 构建：

- 只展示当前账号已获权的共用挂载；
- 不展示挂载 ID、默认个人挂载 ID、物理路径或旧 Space 数据；
- `viewer` 授权或 `read_only` 挂载显示“只读”并禁用写入操作；
- 可编辑挂载以可操作工具栏和行操作表达能力，不显示“可读写”标签；
- 无可用授权时显示“暂无团队文件夹”。

## 5. 文案范围

面向成员的 `myFiles`、个人目录详情、导航、标题、面包屑、空状态、初始化说明和 AI Token 目录边界全部统一为“个人空间” / “Personal space”。

管理员端历史 Space 管理、内部数据模型、API 协议名称和迁移兼容说明不属于本次文案替换范围；不得以 UI 替换为理由恢复旧架构。

## 6. 组件边界

`MemberStorageWorkspace` 负责内容源加载、默认打开个人空间和目录浏览。它将使用独立的视图状态区分 `personal`、`team_folders` 与 `collaborations`，而不是把团队文件夹混入个人空间目录。

`MemberContentNavigation` 只负责三个一级入口。

`MemberContentSourceDirectory` 收缩为团队文件夹的授权挂载目录，不再渲染个人空间卡片。

个人空间和团队文件夹的文件操作通过现有成员文件管理 API 使用统一的内容源 locator；若现有 API helper 仍依赖旧 Space 坐标，必须先补齐对应账户内容源 API helper，不能从新 UI 调用已废弃的 `/api/v1/spaces/...` 路由。

## 7. 测试与验收

自动化测试应覆盖：

1. 侧栏渲染个人空间、团队文件夹和协作，不渲染“我的文件 / My files”；
2. 个人空间进入后直接加载 `source=personal,path=.`，且个人空间标题、面包屑和 AI Token 边界使用新文案；
3. 个人空间显示完整文件管理操作，且不显示“可读写”；
4. 团队文件夹只渲染已授权共用挂载，隐藏挂载 ID；只读挂载显示“只读”且禁用写入操作；
5. 团队文件夹可编辑挂载不显示“可读写”，但可执行完整管理操作；
6. 空个人空间显示“上传文件或新建文件夹即可开始”；无共用授权显示“暂无团队文件夹”；
7. 前端构建、既有 API 契约测试和 release gate 通过。

## 8. 非目标

- 不恢复旧 Space REST API 或旧表依赖；
- 不改变个人目录隔离、授权、挂载身份校验和服务端写入授权；
- 不新增团队文件夹创建、授权管理或物理挂载注册 UI；
- 不把个人空间和团队文件夹的文件混排在同一个根目录。
